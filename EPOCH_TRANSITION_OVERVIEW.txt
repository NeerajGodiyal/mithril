EPOCH TRANSITION OVERVIEW - Mithril
================================================================================
Last Updated: January 2025
Branch: feature/local-rewards-partitions

This document describes how Mithril handles epoch transitions, including leader
schedule computation, rewards distribution, and bank hash calculation.

================================================================================
1. TERMINOLOGY AND TIMELINE
================================================================================

Key Slots at Epoch Boundary (Example: Epoch 905 -> 906)
-------------------------------------------------------
  Snapshot Slot:     391383062  (mid-epoch 905, where AccountsDB state comes from)
  Boundary Slot:     391392000  (LAST slot of epoch 905, where epoch transition runs)
  First Slot E906:   391392001  (FIRST slot of epoch 906)
  First Reward Slot: 391392001  (same as first slot - vote rewards distributed here)

Important Clarification:
  - "Epoch boundary" = the transition point between epochs
  - Epoch transition CODE runs when processing the FIRST slot of the new epoch
  - But the transition MODIFIES state as of the LAST slot of the old epoch
  - Example: When processing slot 391392001, we run epoch transition code that
    computes rewards based on state at slot 391392000

2. EPOCH TRANSITION FLOW (with confidence levels)
================================================================================

When Mithril processes slot N (first slot of new epoch):

  STEP 1: Detect Epoch Boundary [CONFIDENCE: HIGH]
  -------------------------------------------------
  - Compare block.Epoch with currentEpoch
  - If different, we're at epoch boundary
  - Code: pkg/replay/block.go:1494-1500
  - Agave: runtime/src/bank.rs (new_from_parent)
  - FD: fd_runtime.c (fd_runtime_block_execute)

  STEP 2: Prepare Epoch Stakes (prepareEpochStakes) [CONFIDENCE: HIGH]
  ---------------------------------------------------------------------
  - Read StakeHistory sysvar from prevSlotCtx or AccountsDB
  - Compute stake activating/deactivating/effective for all delegations
  - Update StakeHistory sysvar with new entry for the ending epoch
  - Store updated StakeHistory at BOUNDARY slot (prevSlotCtx.Slot)
  - Refresh vote account stakes for the new epoch
  - Cache EpochStakes for leader schedule validation
  - Code: pkg/replay/epoch.go:180-237
  - Agave: runtime/src/stakes.rs (activate_epoch)
  - FD: fd_stakes.c (fd_stakes_activate_epoch)

  STEP 3: Rebuild Vote Cache (RebuildVoteCacheFromAccountsDB) [CONFIDENCE: HIGH]
  -------------------------------------------------------------------------------
  - Read vote accounts from AccountsDB at BOUNDARY slot
  - Extract NodePubkey and vote credits for each vote account
  - This is critical for both leader schedule (needs NodePubkey) and
    rewards (needs vote credits)
  - Missing/closed vote accounts are logged; their stake is ineligible
  - Code: pkg/replay/leader_schedule_local.go:190-350
  - Agave: programs/vote/src/vote_state/
  - FD: fd_vote_program.c

  STEP 4: Build/Validate Leader Schedule [CONFIDENCE: HIGH - VERIFIED WORKING]
  ------------------------------------------------------------------------------
  - Check if snapshot already has schedule for this epoch -> REUSE IT
  - If not, build from vote stakes and validate against RPC
  - CRITICAL: Leader schedule for epoch N uses stakes from epoch N-2 (not N!)
  - The snapshot stores EpochStakes keyed by the TARGET epoch, not source epoch
  - Code: pkg/replay/block.go:1600-1720
  - Agave: runtime/src/bank/leader_schedule.rs
  - FD: fd_leader_schedule.c

  STEP 5: Handle Epoch Rewards (handleEpochRewards) [CONFIDENCE: MEDIUM]
  -----------------------------------------------------------------------
  - If EpochRewards.Active == true: use resume path (don't recompute)
  - If EpochRewards.Active == false: fresh computation
  - Distribute vote rewards (immediate, at first slot)
  - Compute stake rewards and partitions (distributed over following slots)
  - Create/update EpochRewards sysvar
  - Code: pkg/replay/epoch.go:238-280, pkg/replay/rewards.go
  - Agave: runtime/src/bank/partitioned_epoch_rewards/
  - FD: fd_rewards.c (fd_rewards_calculate)

  STEP 6: Process Block Normally [CONFIDENCE: HIGH]
  ---------------------------------------------------
  - Now call ProcessBlock for the first slot of new epoch
  - This executes transactions, computes bank hash, etc.

3. DATA SOURCES AND THEIR PURPOSES
================================================================================

Manifest Data Structures (Different purposes!)
----------------------------------------------
  stake_delegations (manifest)
    - Purpose: Rewards enumeration (list of stake accounts)
    - Contains: Stake pubkeys, delegation info
    - WARNING: credits_observed values are STALE - must refresh from AccountsDB
    - Used for: Iterating stake accounts for rewards
    - Confidence: HIGH that this is understood correctly

  epoch_stakes / VersionedEpochStakes.VoteAccounts
    - Purpose: Leader schedule computation
    - Contains: Vote account pubkeys -> (node pubkey, activated stake)
    - Keyed by: Target epoch (the epoch whose schedule this computes)
    - NOT for rewards - using this for rewards causes miscounts
    - Confidence: HIGH after fixing schedule mismatch

Sysvars
-------
  EpochSchedule: Epoch boundaries, slots per epoch, warmup config
  StakeHistory:  Historical stake activating/effective/deactivating per epoch
  EpochRewards:  Rewards distribution state (Active, total_points, etc.)
  SlotHashes:    Recent slot -> bank hash mappings (for vote validation)
  Clock:         Current slot, epoch, timestamp

Caches
------
  StakeCache:    In-memory map of stake pubkey -> Delegation
                 Loaded from: stake_cache.json (preferred), or rebuilt via
                              stake_pubkeys.idx (point lookups), or AccountsDB scan
                 Updated: Incrementally during replay (recordStakeDelegation)
                 Persisted: stake_cache.json on graceful shutdown/safe panic/cancel
                 Confidence: HIGH

  StakePubkeyIndex: Append-only binary file of 32-byte pubkeys (stake_pubkeys.idx)
                    Flushed: After each block commit, BEFORE state file update
                    Purpose: Fast cache rebuild after crash (point lookups vs full scan)
                    Note: Steady-state ~0 new pubkeys/block; after bulk rebuild
                          first block may append entire cache (deduplicated on load)

  VoteCache:     In-memory map of vote pubkey -> VoteState
                 Rebuilt: At epoch boundary from AccountsDB
                 Contains: NodePubkey, vote credits, timestamps
                 NOT persisted - rebuilt each session
                 Confidence: HIGH

  EpochStakes:   Map of epoch -> (vote pubkey -> stake)
                 Loaded from: Snapshot manifest VersionedEpochStakes
                 Used for: Leader schedule computation
                 Confidence: HIGH

4. LEADER SCHEDULE: THE N-2 RULE [CONFIDENCE: HIGH - VERIFIED WORKING]
================================================================================

Critical Understanding:
  - Leader schedule for epoch N uses stakes computed during epoch N-2
  - Agave stores these stakes keyed by the TARGET epoch N, not source epoch N-2
  - At epoch boundary N-1 -> N, the snapshot already has EpochStakes(N)
  - DO NOT rebuild schedule from current stakes - will cause 99% mismatch

Mithril Implementation:
  1. At epoch boundary, check if snapshot has schedule for block.Epoch
  2. If yes -> REUSE the snapshot schedule (authoritative)
  3. If no -> Build from EpochStakes(block.Epoch) which contains N-2 stakes
  4. Validate against RPC to confirm match

Why Rebuilding Fails:
  - If we rebuild epoch 906 schedule at slot 391392001 using CURRENT stakes,
    we're using epoch 905 stakes (just computed) instead of epoch 904 stakes
  - This causes ~99% leader mismatch because stakes change between epochs

Fix Applied (commit 1c781f8):
  - At epoch boundary, check if EpochStakes(block.Epoch) already exists
  - If yes, don't overwrite with freshly computed stakes
  - Preserves the correct N-2 stakes from snapshot

Reference Implementation:
  - Agave: runtime/src/bank/leader_schedule.rs:leader_schedule_epoch()
  - FD: fd_leader_schedule.c:fd_leader_schedule_new()

5. REWARDS DISTRIBUTION [CONFIDENCE: MEDIUM-HIGH]
================================================================================

Two Paths Based on EpochRewards.Active
--------------------------------------

PATH A: Fresh Boundary (Active == false) [CONFIDENCE: MEDIUM]
  - Crossing into new epoch, distribution hasn't started
  - Compute everything fresh from boundary slot state:
    1. Refresh credits_observed from AccountsDB at boundary slot
    2. Calculate points = stake * (current_credits - credits_observed)
    3. Calculate rewards based on inflation/capitalization
    4. Determine partitions = ceil(eligible_accounts / 4096)
    5. Distribute vote rewards immediately
    6. Set up stake rewards for partitioned distribution
  - Code: pkg/replay/rewards.go:29-200
  - Agave: runtime/src/bank/partitioned_epoch_rewards/calculation.rs
  - FD: fd_rewards.c:fd_rewards_calculate()

PATH B: Resume Mid-Distribution (Active == true) [CONFIDENCE: HIGH]
  - Inside the rewards distribution window (first few slots of epoch)
  - DO NOT recompute totals - use EpochRewards sysvar values:
    - total_points
    - total_rewards
    - num_partitions
    - distributed_rewards
  - Per-account points scaled to match sysvar totals
  - Continue distributing remaining partitions
  - Code: pkg/replay/rewards.go:220-360
  - FD: fd_ssload.c:201-223 (recalc path)

Partition Hashing [CONFIDENCE: HIGH - CRITICAL FIX APPLIED]
------------------------------------------------------------
  Partition assignment uses SipHash13 with the PARENT blockhash:
  - Agave: calculation.rs:747 (epoch_rewards_sysvar.parent_blockhash)
  - FD: fd_epoch_rewards.c:220 (parent_blockhash parameter)
  - Mithril: slotCtx.Blockhash where slotCtx is prevSlotCtx

  IMPORTANT: In Mithril, handleEpochRewards receives prevSlotCtx.
  So prevSlotCtx.Blockhash IS the parent blockhash.
  DO NOT use prevSlotCtx.LastBlockhash (that's the grandparent!).

  Using wrong blockhash causes IMMEDIATE divergence - different accounts
  get assigned to different partitions.

Partition Formula [CONFIDENCE: HIGH - VERIFIED MATCHING]
---------------------------------------------------------
  eligible_accounts = stake accounts with:
    - Valid vote account in cache
    - stake >= minimum_delegation
      (Feature-gated: StakeMinimumDelegationForRewards, StakeRaiseMinimumDelegationTo1Sol)
      (Mithril: NOT YET IMPLEMENTED - currently uses 1 lamport minimum)
    - points > 0 (new credits to earn)
    - rewards > 0 after calculation

  num_partitions = ceil(eligible_accounts / 4096)
  (capped at slots_per_epoch / 10)

  Verified: Local=252, RPC=252 at epoch 905->906 transition

Vote Rewards vs Stake Rewards
-----------------------------
  Vote Rewards:  Distributed immediately at first slot of new epoch
                 Credited to vote accounts
                 Stored at: First slot of new epoch (e.g., 391392001)

  Stake Rewards: Distributed over multiple slots (partitions)
                 4096 stake accounts per partition
                 Each slot in distribution window handles one partition

6. BANK HASH COMPUTATION [CONFIDENCE: MEDIUM]
================================================================================

Bank Hash Formula (with LtHash enabled):
  intermediateHash = SHA256(parentBankHash || numSignatures || blockHash)
  bankHash = SHA256(intermediateHash || ltHash)

Inputs:
  - parentBankHash: Bank hash of the previous slot (from lastSlotCtx.FinalBankhash)
  - numSignatures:  Total signatures in this slot's transactions
  - blockHash:      The PoH hash for this slot
  - ltHash:         Lattice hash of all account modifications in this slot

LtHash Updates [CONFIDENCE: MEDIUM - NEEDS MORE INVESTIGATION]:
  - Computed from writableAccts (accounts that could have changed)
  - Includes: transaction-modified accounts, rent-collected accounts,
    sysvars, epoch-updated accounts
  - Any difference in account state -> different ltHash -> different bankHash
  - Order may matter - need to verify against Agave/FD

Why Bank Hash Matters for Epoch Transition:
  - Slot 391392000 (boundary slot) bank hash is used by votes in slot 391392001
  - If Mithril computes different bank hash, vote transactions will fail
  - VoteErrSlotHashMismatch = vote references hash not in our SlotHashes

Reference Implementation:
  - Agave: runtime/src/bank/bank_hash.rs
  - FD: fd_bank_hash.c

7. SLOT HASHES SYSVAR [CONFIDENCE: HIGH]
================================================================================

Purpose:
  - Stores recent slot -> bank hash mappings
  - Used by vote program to validate vote transactions
  - Maximum 512 entries, oldest evicted when full

Update Timing:
  - When processing slot N, we add entry for slot N-1 (parent slot)
  - Entry contains: (parentSlot, parentBankHash)
  - This means slot N-1's hash is visible to transactions in slot N

Vote Transaction Validation:
  - Vote tx includes the hash it's voting for
  - Vote program looks up that slot in SlotHashes
  - If hash doesn't match -> VoteErrSlotHashMismatch
  - This is how bank hash divergence manifests as vote failures

================================================================================
8. ACCOUNT MODIFICATION TIMING [CONFIDENCE: MEDIUM-HIGH]
================================================================================

Accounts Modified at Epoch Boundary:
  Stored at BOUNDARY slot (last slot of old epoch):
    - StakeHistory sysvar (updated with new epoch entry)

  Stored at FIRST slot of new epoch:
    - Vote accounts (vote rewards credited)
    - EpochRewards sysvar (created/updated)
    - Stake accounts (during partitioned distribution)

This timing matters because:
  - Bank hash of boundary slot should NOT include vote rewards
  - Vote rewards are reflected in bank hash of first slot of new epoch
  - If timing is wrong, bank hash will diverge

EpochUpdatedAccts Flow:
  - Epoch transition code populates block.EpochUpdatedAccts
  - These accounts are included in bank hash calculation via compileWritableAndModifiedAccts
  - ParentEpochUpdatedAccts captures pre-modification state for ltHash delta

9. RESUME AND PERSISTENCE [CRITICAL FOR RELIABILITY]
================================================================================

Mithril must be able to resume after:
  1. Graceful shutdown (Ctrl+C, SIGTERM)
  2. Panic during replay (crash recovery)
  3. System restart

Key Persistence Files:
  mithril_state.json    - Last committed slot, bankhash, resume context
  stake_cache.json      - Full stake cache (1.2M entries, ~200MB)
  stake_pubkeys.idx     - Binary index of stake pubkeys (append-only, ~38MB)
  bankhash.log          - Debug log of bank hash computations

Resume Flow [CONFIDENCE: HIGH]:
  1. Load mithril_state.json to get last committed slot
  2. Try to load stake_cache.json (exact slot match required)
  3. If stale/missing, try stake_pubkeys.idx for fast rebuild via point lookups
  4. If no index, fall back to full AccountsDB scan (30+ minutes)
  5. Resume replay from last committed slot + 1

Stake Cache Persistence [CONFIDENCE: HIGH - NEWLY IMPLEMENTED]:
  - stake_cache.json: Full cache saved on graceful shutdown
  - stake_pubkeys.idx: New pubkeys appended after each block commit
  - On resume: index enables ~1M point lookups instead of ~200M full scan
  - Compaction: Index rewritten with current cache at shutdown

Mid-Block Crash Handling [CONFIDENCE: HIGH]:
  - blockReplayInProgress flag tracks if we're mid-block
  - If panic mid-block: don't save stake cache (has uncommitted updates)
  - Resume from last COMMITTED slot (N-1), not crash slot (N)
  - Clear pending stake pubkeys on mid-block crash

Critical Invariant for Resume:
  - stake_cache.json slot MUST match mithril_state.json LastSlot
  - If mismatch, cache is stale -> use index or scan
  - Any stake changes between cache slot and resume slot would be missing

13. DEBUGGING TIPS
================================================================================

If Leader Schedule Mismatches:
  1. Check which EpochStakes are being used (should be epoch N for schedule N)
  2. Verify snapshot schedule is being reused if available
  3. Check logs for "[LEADER SCHEDULE]" entries
  4. Compare hash against RPC validation file
  Confidence in diagnosis: HIGH

If Partition Count Mismatches:
  1. Check eligible account count
  2. Verify credits_observed was refreshed from AccountsDB
  3. Check for vote cache rebuild errors
  4. Compare total_points against RPC EpochRewards sysvar
  Confidence in diagnosis: HIGH

If Bank Hash Diverges:
  1. Check "BANKHASH INPUTS" log at epoch boundary
  2. Compare parentBankhash, numSignatures, blockhash
  3. Check ltHash pre/post values
  4. Verify account modification timing
  Confidence in diagnosis: MEDIUM (ltHash is complex)

If Vote Transactions Fail:
  1. VoteErrSlotHashMismatch = bank hash divergence at referenced slot
  2. Check which slot the vote references
  3. Compare that slot's bank hash with RPC
  4. Trace back to find where divergence started
  Confidence in diagnosis: HIGH

If Resume Fails / Full Scan Triggered:
  1. Check stake_cache.json slot vs mithril_state.json LastSlot
  2. Check if stake_pubkeys.idx exists
  3. Check if crash was mid-block (cache not saved)
  4. Look for "stake cache stale" warnings in logs
  Confidence in diagnosis: HIGH
