## A) Partition Count Mismatch (Local 250 vs RPC 252)

Symptoms (recent logs):
- eligible=1,023,378 -> partitions=250
- RPC expects 252 (4096 per partition)
- local total_points=0x713e16bb659b55c1e5a51
- RPC sysvar total_points=0x26af60a4c2e303bda8f2d
- total_rewards sometimes differs slightly (~6,120,918 lamports)

Key finding:
- Local total_points is ~3x RPC total_points.
- This shifts the reward threshold and changes eligibility/partition count.
- We now warn on mismatch and can fall back to RPC EpochRewards sysvar totals
  (points/rewards/partitions) as a temporary recovery path.

Likely causes:
1) Points calculation input mismatch (credits_observed / vote credits history).
2) Feature gate mismatch (min_stake_delegation reads as 0), though this alone
   does not explain the 3x total_points gap.

Next steps:
- Verify the vote credits source matches the boundary slot or the sysvar path.
- Confirm credits_observed refresh is applied before points computation.

## B) Rewards Recalculation vs Fresh Distribution

Firedancer behavior:
- If epoch_rewards.active == true:
  - Do not recompute total_points/total_rewards.
  - Use EpochRewards sysvar totals and prev vote credits snapshot.
- If epoch_rewards.active == false:
  - Compute from boundary slot state (last slot of previous epoch).

Mithril behavior:
- Historically recomputed points even when rewards were active on resume.
- Guard is needed to prefer sysvar totals in the active path.

Relevant FD references:
- firedancer/src/flamenco/rewards/fd_rewards.c:1088-1165
- firedancer/src/discof/restore/utils/fd_ssload.c:201-223
